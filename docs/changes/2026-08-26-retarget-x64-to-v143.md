# 2026-08-26 — Retarget Windows x64 to MSVC v143 and get it linking

## What changed

The `x64` configurations of both projects now build with the VS2022 `v143`
toolset instead of `v110`, and `MinecraftPC.sln` produces a working
`Minecraft.Client.exe` on a machine with no VS2012 installed.

Full background in [`systems/windows-x64-modern-msvc-build.md`](../systems/windows-x64-modern-msvc-build.md).

## Why

VS2012 is not practically installable today, so the x64 target — the only
realistically buildable configuration in the tree — could not be built at all.

## Files

**Toolset**
- `Minecraft.World/Minecraft.World.vcxproj` — 7 `x64` configs `v110` → `v143`
- `Minecraft.Client/Minecraft.Client.vcxproj` — 7 `x64` configs `v110` → `v143`,
  plus a new `ClCompile` item for the CRT shim

Only `|x64` property groups were touched. `Win32`, `Durango` and `ARM64EC` remain
`v110`; the console toolsets are untouched. **The 7th-gen solutions are unaffected.**

**Source fixes (4 files, 2 root causes)**
- `Minecraft.World/x64headers/extraX64.h` — `hash_value()` shim, guarded by
  `_MSC_VER >= 1900`
- `Minecraft.World/Player.cpp` — `std::hash_value` → unqualified `hash_value`
- `Minecraft.World/I18n.{h,cpp}`, `Minecraft.World/Language.{h,cpp}` — last named
  parameter before `...` changed from `const wstring&` to by-value `wstring` so
  `va_start` is legal

**New**
- `Minecraft.Client/Windows64/Win64CrtCompat.cpp` — x64-only shims for `__iob_func`
  and `std::_Winerror_map`, which the prebuilt VS2012 4JLibs still reference but the
  UCRT no longer provides

**Vendored (needs a decision — see below)**
- `Minecraft.Client/Windows64/4JLibs/libs/{4J_Input,4J_Storage,4J_Render_PC}.lib`

**Other**
- `.gitignore` — ignore `/Builds/`

## Unverified

- **The executable has never been run.** It compiles and links; that is all that was
  checked. No launch, no gameplay, no rendering, no audio.
- Whether the game needs original media beyond what the post-build steps stage.
- Whether `hash_value` forwarding to `std::hash` matches the old `<xhash>` helper
  exactly. It does not matter for either call site (one is dead code, the other is an
  in-memory hash that already varies by platform), but it was not verified.
- Whether the `Debug|x64` and the various `ContentPackage` x64 configurations build.
  Only `Release|x64` was exercised.
- Nothing was rebuilt for Win32/Durango/ARM64EC or any console target, so "unaffected"
  is reasoned from the config conditions, not observed.

## Watch out

1. **Vendored `.lib` files are modified in the working tree.** To clear the
   `LNK2038` `_MSC_VER` mismatch, the string `FAILIFMISMATCH:"_MSC_VER=1700"` was
   rewritten in place to `FAILIFMISMATCH:"_MSC_VXR=1700"` — same byte length, so the
   key simply stops colliding with our own `_MSC_VER` directive. Applied to
   `4J_Input.lib` (7 occurrences), `4J_Storage.lib` (5) and `4J_Render_PC.lib` (8).
   Reversible with `git checkout -- Minecraft.Client/Windows64/4JLibs/libs/`, which
   will also stop the build linking until it is redone.

   **Resolved:** the owner has confirmed that modifying vendored binaries is
   acceptable and in keeping with the goals of the fork. CLAUDE.md was updated on
   the same day to permit it, with guidance on doing it safely. No build-time
   copy-and-patch step is needed. Note the edit does not show up in a `git diff`,
   which is why the exact byte change is spelled out here.

2. **Cross-CRT STL.** `4J_Storage.h` / `4J_Profile.h` pass `std::string`, `wstring`
   and `std::vector` between VS2012-built and VS2022-built code. This links but is
   unsupported. First suspect for weird runtime behaviour in save/DLC/profile paths.

3. Build the `.sln`, not the `.vcxproj` — the link line needs `$(SolutionDir)`.

## Correction to existing docs

`docs/README.md` previously stated agents cannot compile this project. That is no
longer true — VS2022 is present and MSBuild is drivable from the agent shell. The
ground rule has been rewritten to require that a build claim be backed by an actual
build, and that runtime behaviour still never be claimed without the owner running it.
